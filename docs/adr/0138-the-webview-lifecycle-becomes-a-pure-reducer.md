# The webview lifecycle becomes a pure reducer

**The document editor's mount-once-then-message webview lifecycle is extracted to a PURE reducer (`common/editorWebviewProtocol.ts`) so the timing-sensitive path (first-render setHtml, hold-render-until-ready + flush, pmReset only on a model-driven body change, focus-after-navigate) is unit-tested; `livingDocEditor.ts` becomes a thin effect-runner**

Settled to the plan's iteration-5 (P2-3 debt) recommendation for the editor lifecycle. The mount-once-then-message webview (decision 50: the 496 KB PM shell is set via setHtml ONCE, later renders go over postMessage so the live ProseMirror surface is never torn down) is exactly the timing-sensitive code the review flagged as untested. Its state machine is now a pure reducer: `applyRender` (first render -> setHtml effect + initialize; a render while ready -> a postRender effect carrying pmReset only when the body changed from a model-driven source; a render before ready -> hold as pendingContent), `applyReady` (flush the held render with NO pmReset - it is the mounting body, not a live change - then flush any held focus target), `applyFocusRequest` (post immediately when ready, else hold until ready), and `recordPmBody` (the user's own typing suppresses the next spurious pmReset). The editor holds the `IEditorWebviewState` and carries out the returned effects against its webview via a small `_runProto`; the five ad-hoc lifecycle fields + the inline `_flushFocusChange` are gone (the class shrank measurably). **Deviation (logged):** `screenEditor.ts` was NOT given a reducer - it uses whole-screen `setHtml` on every render (mount-fresh on each visibility, no mount-once message protocol) and its message handler already routes straight to service methods, so there is no timing-sensitive lifecycle to extract; the meaningful P2-3 extraction is the `livingDocEditor` mount-once path, which is where the silent-regression risk lives. **Tier: our-surface, 0 core patches** (new `common/editorWebviewProtocol.ts`, `browser/livingDocEditor.ts` rewired to the reducer). Verified: 9 pure reducer tests covering exactly the plan's named cases - first-render setHtml-once; a pre-ready render held then flushed with no pmReset; a model-driven body change resets while a chrome-only render does not; recordPmBody suppresses the spurious reset; a null-body render clears the tracked body; focus-before-ready held + flushed; focus-after-ready immediate; ready flushes render-before-focus; an empty ready is a no-op. Behaviour is preserved (the effects are byte-for-byte the messages the old inline code posted); a live open/edit/approve/navigate smoke on `:8080` was blocked by the same pruned-node_modules web build, documented at `docs/plans/30-verify/README.md`. No evidence fabricated.
