# The fan-out packs context-bounded batches

**The whole-project fan-out packs the working set into context-bounded BATCHES (estimate chars/4, budget `livingDocs.fanoutContextBudget` default 24k), runs the batches in order, merges the per-batch keyed edits, and flags a document too large for the budget as "too large for this run" - never a silent truncation**

Settled to the plan's D30-B recommendation. The plan-18 fan-out (decision 62) sent EVERY working-set body in one call, so a 50-doc folder silently overflowed the context window. A pure `common/fanoutBudget.ts` (`estimateTokens` = `chars/4`, `planFanoutBatches(docs, contextBudget, promptOverhead)`) packs the docs greedily in order into batches whose summed body cost fits `contextBudget - promptOverhead` (floored at 512 so a mis-sized overhead can't wipe the budget); a document whose OWN body exceeds the per-document budget is set aside as `oversize` (never sent, never truncated). Each non-oversize document lands in EXACTLY one batch, so the per-batch keyed replies concatenate into the pending queue with no double-count or drop (uniqueness by construction); the merge is further restricted to the batch's own documents so a reply naming an out-of-batch doc cannot route an edit to a document that batch never showed. `_chatRespondMulti` runs the batches SEQUENTIALLY (the first streams its prose into the live turn; later batches use the model-limiter-bounded buffered `_callModel`), emits a `Batch K of M` step per batch and a `too large for this run` step per oversize doc, and publishes an `IFanoutProgress` (batch index/count + oversize docIds) the project-run screen reads: the command strip shows a `Batch K of M` chip while a run spans >1 batch, oversize documents' swarm tiles render an amber "too large for this run" state (excluded from the live working overlay), and the bottom bar reports an `N too large` bucket. `summariseProjectRun` gained an `oversize` tile status + `oversizeDocs` count; the budget is a user-overridable number setting (`livingDocs.fanoutContextBudget`, min 2000, default 24000). **Tier: our-surface, 0 core patches** (`livingDocsService.ts`, new `common/fanoutBudget.ts`, `common/livingDocs.ts` interface, `common/livingDocsModel.ts` summary, `browser/screenRender.ts` + `browser/screenEditor.ts` UI, `browser/livingDocs.contribution.ts` config). Verified: 6 pure `fanoutBudget` tests (chars/4 estimate; single batch when it fits; ordered split at the boundary with every doc packed once; oversize set aside; overhead floor; empty set) + 1 `summariseProjectRun` oversize test + 2 service tests (over-budget set sent in 2 batches with edits merged to the right docs one-each + batch steps + progress; oversize doc flagged/never sent/others still change - the single-doc/no-working-set path is covered by the pre-existing D-B test, which still passes against the batched path) + 3 `screenRender` tests asserting the UI from the pure render (the `Batch 2 of 3` chip; no chip for a single batch or a not-yet-started batch; the amber "too large for this run" tile + the `1 too large` bottom-bar bucket) - all MEASURED against the mock, numbers in `docs/plans/30-verify/notes.md`.
