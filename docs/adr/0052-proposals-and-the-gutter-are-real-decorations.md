# Proposals and the gutter are real decorations

**Pending proposals + the provenance gutter are real ProseMirror decorations; accept/reject route through the existing service and the live body resets after a model-driven change**

Iter 4 had to bring the last `renderDoc`-only features (F4 inline diff, F6 accept/reject, G5 gutter, the source drawer) onto the PM surface before the default could flip (decision 49). Two mechanisms for accept were possible: (a) the plan's literal sketch — a PM transaction in the bundle replaces oldText->newText / splices the insert, then `toMarkdown -> withReplacedBody -> saveRawText`; (b) route accept/reject through the **existing** `service.approve/reject` (which already mutates blocks, re-anchors claims, writes the lock + audit, and persists) and reset the live PM body to disk truth afterwards. Chose **(b)**: it is DRY (no second copy of the mutate/persist logic), correct for inserts (where (a) would double-apply once the reparsed block shifts), and keeps the rail trivially in sync (the proposal just leaves `_pending`). The decoration spec is a TDD'd pure mapping (`buildPmDecorationSpec`: proposal[] + doc -> serializable spec); the vendored bundle gains a decorations plugin + `setDecorations(view, spec)` (text-anchored: a pending edit hides its block and renders the diff+controls widget in its place; an insert is an all-additions widget after its anchor; bound blocks get a gutter dot) + `setDoc(view, md)` (reset the doc content without remounting the view). Widget HTML is host-rendered with the renderDoc markup so the look is identical. PM is fed from the **reparsed** body (`parseLivingDoc(rawText).body`) because `approve`/`editBlock` mutate blocks + persist but leave the cached `doc.body` stale; a render whose fresh body differs from what PM holds (an accepted proposal - never the user's silently-saved typing) ships a `pmReset`. **The default did NOT flip this iteration** (the plan's explicit fallback): decoration parity is complete in PM, but the calm CHROME (the persistent formatting toolbar wired via `execCommand`, and the Present button) is still `renderDoc`-only, so flipping would regress the G2 / v2-v4 calm-toolbar gates; porting the toolbar to `LWDPM.cmd` + Present into PM, then flipping + retiring the `renderDoc` body, is iter 5.
