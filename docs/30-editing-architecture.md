# 30. The editing architecture

**Status:** architecture of record for the agentic editing layer. Produced 20 Aug 2026 by a six-member expert council (agent systems, applied LLM/inference, document and editor systems, review experience, retrieval and context, correctness and trust) chaired against `main` at `f8f0078cd4c` on branch `fix/openrouter-curated-models`.
**Input:** [29-chat-quality-and-multi-doc-architecture.md](29-chat-quality-and-multi-doc-architecture.md) is the brief this document resolves. The brief was treated as evidence, not scripture: every load-bearing claim was re-verified against the code, and section 8 records where the brief was wrong.
**Rulings:** the six questions in section 9 were answered by the founder on 20 Aug 2026; the rulings are recorded there and folded into 2.2, 2.3, 2.6, 4.6 and 10.
**Rule of the record:** every claim about the current system carries a `file:line` citation, verified first-hand during the council session. D2 and D4 were settled by the founder before the council sat; this document designs them and does not reopen them.

## Why this document exists

One conversation must be able to update an entire project of documents, rewrite a whole document where the instruction calls for it, and present every change as a line-by-line diff a person can trust. The brief diagnosed why today's single-shot JSON-in-prose contract cannot get there. This document is the architecture that can: what to build, in what order, with the invariants that make the product's trust wedge structural rather than aspirational. The north star throughout is the user's experience - each decision below is justified by what the person using Abstract sees, feels and can rely on, not by architectural elegance.

## 1. The architecture in one page

**Models author content, never coordinates. The host owns all geometry.** Every defect family the council traced (#300, #303, #329, #334, the id delusion) came from letting quoted text stand in for positions, or letting a count be re-derived after the fact. The whole design is that principle applied everywhere:

1. **A renderer-hosted agent loop** (D4, D5): a pure, hand-rolled tool-use kernel in `common/`, driving eight tools whose executors live beside the document state. The broker stays a stateless translating proxy and gains tool passthrough, per-request model pinning, prompt-cache forwarding and a reasoning knob. No framework is adopted.
2. **A two-lane edit wire** (D1, D2): for targeted edits the planner emits a structured segment list over ordinal-labelled blocks (`{keep: "B1-B7"}, {replace: "B8-B9", content}`) and the host expands it deterministically - no apply model, zero latency, unchanged bytes byte-identical by construction. For whole rewrites the planner authors the full body in dedicated parallel per-document calls that land progressively. A hosted fast-apply model (Morph) is an optional lane behind a measured trigger, not the spine.
3. **A persisted change store** (D1, D6, D8): the host diffs base to proposed at block granularity; every hunk becomes a durable `Change` with a uuid, a base-revision hash, a rebasable span, stacking versions and an optional comment thread. The store is the single authority for counts, verbs, receipts and the audit trail. Bulk verbs exist only as `captureBulkSet(scope) -> {ids, sentence}`; the applied set can shrink from the confirmed sentence, never grow.
4. **Scope by signal, then by planner** (D3): explicit attachments are the scope, enforced fails-closed at the store's write boundary. Everything else routes through the planner with the document catalogue in context, a visible scope strip, a consent gate before wide runs, and a deterministic content-overlap backstop that names what was left out. Retrieval is lexical + frontmatter + wikilink graph behind a stable `search_documents` contract; no embeddings at v1.
5. **Review is diff-first at every scale** (D6): the shipped three-level hierarchy is completed (previous-document control, one coherent change-set model) rather than rebuilt. Rewrite-class documents keep line-by-line diffs as the default view and move the primary decision to the document level with per-hunk drill-in. Comment becomes a third verb; a change under discussion is structurally excluded from every bulk sweep.
6. **Invariants, journalled** (D8): apply outcomes are a closed result type; approvals are written only by the code path that mutated the document, carrying the post-state hash; an intent journal with declared expected post-hashes makes crash recovery a matter of proof, not suspicion. A second model pass is advisory only. Deterministic checks carry the guarantees.

## 2. The decisions, resolved

| # | Decision | Resolution |
|---|---|---|
| **D1** | Edit representation | **File-level operations at the wire (`rewrite`, `create`, `delete`, `rename`), carried as segment lists for targeted edits and full bodies for rewrites; diffed locally into a persisted change store.** Rejected: hardened anchored search/replace; model-emitted block operations. |
| **D2** | Planner/apply split (settled) | **Designed as: deterministic host expansion for targeted edits; planner-authored bodies for rewrites, parallelised; Morph `morph-v3-fast` as an optional lane via the existing OpenRouter door.** No third door. Requires per-request model pinning (new defect, 2.2). |
| **D3** | Retrieval and scope | **Tiered: deterministic on explicit signals; planner-classified residue with visible scope and consent; lexical + metadata + graph retrieval behind `search_documents`.** Rejected: embeddings at v1; a dedicated classifier call; "always retrieve". |
| **D4** | Agent loop (settled) | **Designed as: renderer-hosted kernel, eight tools, bounded by a declared scope contract, a step ceiling and a per-task budget with wave-level pre-authorisation.** No wall-clock bound. |
| **D5** | Framework | **Stay hand-rolled: a pure loop kernel in `common/`, typed against `@anthropic-ai/sdk` types only.** Rejected: reusing the upstream `agentHost` subsystem; the SDK `toolRunner`; Vercel AI SDK; LangGraph. |
| **D6** | Review at scale | **Complete the shipped hierarchy; asymmetric directional bars; comment as a third verb over an orthogonal thread state; a declared per-document change class switching the decision unit.** |
| **D7** | Cost and latency | **Append-only context with cache breakpoints and sticky sessions; digest-only transcripts; per-purpose output caps, concurrency and reasoning effort; wave budget pre-flight.** Roughly 50-60% task-level cost reduction and sub-second per-step time-to-first-token. |
| **D8** | Verification | **Invariants I1-I8 enforced at the store's write boundary, an intent journal with a startup reconciler, deterministic post-checks always; a second model pass advisory-only.** |

### 2.1 D1 - the edit representation

Today's pipeline resolves an edit's target by string matching three separate times, in three layers that fail differently and silently: queue-time fuzzy token similarity with a bare `return undefined` on miss (`livingDocsService.ts:6209-6221`, `similarity` at `:322`), apply-time exact `indexOf` with a silent no-op on miss (`livingDocMarkdown.ts:756`, `:759`), and render-time strict text equality against top-level ProseMirror nodes (anchors built at `livingDocPmDecorations.ts:186-205`). Those are, respectively, the #303, #329 and #300 defect families. Hardening option (a) means hardening three matchers whose shared root is the representation itself; it also cannot express a whole-document rewrite, a heading rename (`_queueChatEdit` skips heading blocks outright, `livingDocsService.ts:6211`) or a document split.

Option (c), model-emitted block operations, rests on a premise the council disproved: block ids are not stable. They are content-derived for headings and ordinal for everything else, regenerated on every parse and every typed save, collide on duplicate headings, and are deliberately absent from disk (`livingDocMarkdown.ts:470-479`, `:14-16`; re-parse per save at `livingDocsService.ts:3814-3820`; probe-confirmed instability and `h-notes` collisions). An id a model must target is a position by another name, which is Cursor's third objection re-imported.

The resolution takes Cursor's conclusion (whole units, no model-owned positions) without cargo-culting its mechanism. The model-facing contract is file-level: `rewrite(doc, body)`, `create(doc, body)`, `delete(doc)`, `rename(from, to)`. Content arrives two ways:

- **Targeted edits: a segment list.** The document is serialised to the planner with ordinal labels printed beside each block (extending `_serializeDocForChat`, `livingDocsService.ts:6316-6324`, with the same address space the gutter already zips positionally, `livingDocPmDecorations.ts:270-276`). The planner emits `{keep: "B1-B7"} / {replace: "B8-B9", content} / {insertAfter: "B14", content}`, schema-enforced. The model copies labels adjacent to content it just read; it never counts and never quotes anchors. Each `replace` also echoes the first words of the blocks it replaces, so a syntactically valid but off-by-one range becomes a hard validation failure rather than a silent misapply. The host expands the list deterministically.
- **Rewrites: a full body**, authored by the planner (the prose must be planner-quality; a mechanical apply model cannot write the frontier model's sentences), emitted inline for small documents and in dedicated parallel per-document calls for large ones.

Either way the host then computes one deterministic block-granularity alignment (unique-content anchor pass, Jaccard pairing between anchors, word-level LCS inside modified pairs - all reusing shipped pure functions, `livingDocPmDecorations.ts:205-250`) and compiles the result into persisted `Change` objects. Approve splices approved hunks into `rawText` and never routes the document through `serializeLivingDoc`, which quarantines a live data-loss bug: the serialiser drops frontmatter the parser reads, including the `fromTemplate` provenance field (parse `livingDocMarkdown.ts:441-456` vs emit `:769-789`, written through on every approve at `livingDocsService.ts:6744-6751`).

Bindings become guaranteed rather than refused. Today bound prose is simply un-editable and the refusal is silent (`:6212-6215`, `:6226`), and the model cannot preserve bind markup because serialisation resolves it away before the model ever sees it (`:6316-6324`). Under the new wire the model sees the markup (or a stable placeholder per key) and the host enforces a local invariant on every returned body: the bind-key multiset of the base must survive with well-formed markup (`extractBindLinks`, `livingDocMarkdown.ts:23-29`), or the offending hunk is rejected into review. Frontmatter never enters model scope at all; the host re-attaches it via `withReplacedBody` (`livingDocMarkdown.ts:666`).

**Change identity** (the 1.4 requirement): each hunk is a `Change {id: uuid, setId, anchors: [{docUri, baseRevision, span, oldText, newText}], status, plannerIntent, changeClass, versions[], thread[]}`. Identity is decided by provenance, not geometry: human edits underneath never re-diff a change (spans remap through the document's edit map; an intersecting human edit flips the change to `needs-attention` on the same id); an agent revision answering a thread re-diffs and folds overlapping hunks into a new version on the same Change, spawning non-overlapping ones as siblings tagged `spawnedBy`; a later turn over the same region supersedes with a `supersededBy` pointer rather than versioning. Threads and history survive every path. The anchors array carries cross-document moves as one Change with one decision from day one, with detection deferred.

`changeClass` (`targeted | rewrite`) is derived from alignment statistics (changed-character ratio >= 0.6, the document-level echo of the design system's ~60% word-grain rule, `docs/28-design-system-round2.md` Components), with the planner's declared intent stored as advisory provenance; a mismatch between the two is a free quality signal.

### 2.2 D2 - who serves what

The emit matrix, agreed after the council's sharpest exchange (the inference engineer formally withdrew Morph-as-spine):

| | Small doc (~1KB) | Large doc (~10KB) |
|---|---|---|
| **Targeted edit** | Planner emits segments; host expands, ~0s | Same; abbreviation pays most here |
| **Whole rewrite** | Planner emits the body inline (~4s) | Planner authors the body in a dedicated parallel call (~35-45s each, overlapped) |

Fast-apply models exist to expand fuzzy lazy edits; once the wire carries explicit keep-ranges, expansion is deterministic string assembly and a model in that path is pure added risk. Morph (`morph/morph-v3-fast`, $0.80/$1.20 per Mtok, ~10.5k tok/s vendor-claimed, served by OpenRouter itself so it costs one registry row in `scripts/lwd-openrouter-models.js`) is retained as: a paste/import merge lane, a weak-planner fallback, and a measured escape hatch - if a planner model's segment schema-violation rate exceeds ~5% of turns in the validation walk, that model falls back to lazy edits + Morph rather than prompt-tuning heroics. Its prose/frontmatter fidelity is unmeasured (all published benchmarks are code) and must be probed before any promotion.

Serving plan: on the ChatGPT OAuth door, `gpt-5.6-terra` plans (Codex-tuned, tool-native, free to the founder). On the included OpenRouter tier, serve **`anthropic/claude-sonnet-5`** as both the planner and the rewrite author (approved, ruling 9.3) - Sonnet 4.6 is absent from Anthropic's structured-outputs support list, and Sonnet 5 carries intro pricing ($2/$10 to 31 Aug). `openai/gpt-4.1` is the fallback; `gpt-4.1-mini` is demoted from default (its own catalogue notes blame it for #303, `lwd-openrouter-models.js:54-55`). Rewrite calls run at minimal reasoning effort with per-document output caps - on reasoning models a "mechanical" rewrite can otherwise burn 5-20s thinking before the first body token, which would double every wall-clock figure above.

Two broker facts make this currently impossible and are scheduled first. There is **no per-request door pinning**: the door is chosen before the model (`selectBackend()` at `lwd-model-broker.js:844`) and the id resolves against that door's list only (`:852-853`), so planner-on-OAuth plus apply-on-OpenRouter in one turn is unroutable, and while signed into ChatGPT the included-tier picker is silently decorative. And **tool calls are unrepresentable in both directions on both doors** (bodies at `:379` and `:482-491`; content flattened at `:297-308`; stream parsers text-only at `:422-427` and `:499-523`). The fix: a merged catalogue where the model id implies the door (OAuth entitlement preferred on collision, overridable in `~/.abstract/models.json`), an advisory `purpose: plan | apply | chat` field that resolves per-lane defaults and stamps the spend audit, and loud failure - no silent cross-door substitution, ever, because that is the F1 bug class this branch just fixed. A pinned door down pauses that lane honestly.

No first-party Anthropic door now. The old one died with Anthropic's subscription-OAuth ban (`lwd-model-broker.js:27-28`); a new one means the founder's API key plus a hand-rolled price table, while OpenRouter already reaches the same models with full `cache_control` passthrough and authoritative `usage.cost` metering. Revisit on a demonstrated feature gap (strict structured outputs that do not pass through, Anthropic fast mode) or material scale. The phantom client default `DEFAULT_MODEL = 'claude-opus-4-8'` (`livingDocsService.ts:202`), which routes nowhere and is silently swapped by `resolveRequestedModel` (`:793-800`), is deleted; the client sends no model and the catalogue decides.

### 2.3 D3 - scope and retrieval

**Tier 0 fires only on explicit signals.** Attachment chips present: exactly those documents. Folder chip: that folder - which must be built; today `addFolderToWorkingSet` takes no folder URI and adds every document across the workspace (`livingDocsService.ts:5585-5588`, `:1250-1252`), so the brief's "folder = that folder" row describes a requirement, not behaviour. Explicit scope is enforced fails-closed at the change store's write boundary: a `plan_scope` that widens past an explicit signal returns a typed `scope_locked` error the model relays in words ("ask the user to widen"); the user's reply is itself a new explicit signal. Narrowing is always silent. Out-of-scope *reads* stay permitted but ledgered (adopted by founder ruling 9.4).

**Everything else routes through the planner.** There is no honest deterministic reader of unbounded language ("make every doc consistent with the new pricing" contains no trigger phrase), so no keyword matcher guards the residue. Instead the planner always has the catalogue in its cached prefix (~300 tokens for the sample corpus, ~8k at a hypothetical 200-document corpus), must declare `plan_scope(docIds, rationale)` before any tool that proposes changes unlocks, and the declaration renders as a visible scope strip - an under-scope becomes a visible claim sitting under a prompt that contradicts it, recoverable in one click. A deterministic content-overlap backstop inverts the detection direction: after planning and again at run end, the lexical index checks the instruction's salient terms against out-of-scope documents and names the residue ("3 other documents mention the old pricing - widen and re-run?"). Its failure mode is a lost hint, never a wrong scope.

**The retriever is lexical + metadata + graph, and that is a decision, not a deferral.** The sample corpus is 11 documents totalling 7,850 bytes; even a heavy user's corpus (200 x 5KB) is grep-instant and self-describing - frontmatter already carries eleven typed fields including `sources`, `context`, `status`, `tags` and `policy` (`livingDocMarkdown.ts:421`, `:445-458`). An embedding path would add a model dependency, a store, invalidation and a privacy surface to beat kilobyte-scale lexical search. The per-workspace catalogue (title, subtitle, headings, tags, policy, declared sources, outgoing wikilinks, derived backlinks, approx tokens) is built lazily from the existing scan (`listDocuments` `:1243`, `_collectDocs` `:1252`), invalidated per save by a correlated watcher, held in memory, rebuilt in under a second. `search_documents(query)` returns doc-level hits with block-level excerpts, ranked title > heading > body, boosted by graph adjacency and shared declared sources. The wikilink grammar is fully specified and parsed (`common/wikilinks.ts:206-219`) but has zero production callers and the sample corpus contains zero wikilinks - the graph is a cheap bonus signal, never load-bearing, until real corpora prove link density. The tool contract is the seam that makes revisiting embeddings cheap.

**Scope's store of record** is the persisted session/change-set store, not `_workingSets` (in-memory, keyed per anchor document URI while chats key per session - `livingDocsService.ts:559`, `:5562-5563` vs `:5324-5327`; persisting the map would fossilise the keying bug). The session record carries live scope as pins and agent-added fills with consent state; each `ChangeSet` snapshots the scope a turn actually ran against, which is what surgical retry replays. `_workingSets` survives as a derived view.

### 2.4 D4 - the loop

The loop lives in the renderer because the state its tools mutate lives there: the policy gate (`livingDocsService.ts:6203-6204`), the bind guards (`:6226-6227`), the pending pipeline (`:6246`) - and because the renderer is the only place the code runs unmodified on desktop and web. The broker stays per-request stateless. The upstream `agentHost` subsystem (see 2.5) proved the separate-process pattern and also why it is wrong here.

**The tool surface (eight verbs, all executors renderer-side):**

| Tool | Contract |
|---|---|
| `list_documents()` | Catalogue rows: docId, title, headings, status, policy (locked docs marked, enforcement stays host-side), approxTokens |
| `read_document(docId, heading?)` | Ordinal-labelled block serialisation; each read is an appended event pinned for caching |
| `search_documents(query)` | The D3 retriever behind a stable contract |
| `read_source(name, range?)` | Attached source text, ranged |
| `plan_scope(docIds[], rationale)` | Declares/renegotiates scope; pre-filled and gate-free when scope was explicit; typed `scope_locked` error on widening past an explicit signal |
| `propose_segments(docId, segments[])` | The only in-loop mutating verb. Host expands, diffs, writes via the store, returns per-segment receipts: `queued(changeId) \| dropped(policy \| bind-guard \| stale-ordinal \| out-of-scope \| no-op)` |
| `rewrite_documents(jobs[])` | Dispatch-and-await. Bodies stream outside the loop into the store; the tool returns digest receipts only (`{docId, status, changeIds, sizeDelta}`), one loop step regardless of batch width |
| `finish(summary, flags?)` | Mandatory terminal. The model authors narrative only; the host composes the authoritative per-document ledger from store receipts and rejects a `finish` while jobs are unsettled |

Rewrite bodies never enter the transcript: 20 bodies would be 30-50k tokens re-paid as input on every subsequent step; digests cost ~50-100 tokens each. If the planner needs a body back it reads it through a tool call and pays for what it reads.

**Bounds, three layers, no wall clock:** the scope contract (the real bound - changes against undeclared documents are typed errors); a step ceiling (default 20, `livingDocs.agentMaxSteps`, plus a per-document failure ceiling of 3 preserving partial-success semantics); and a per-task token budget derived from the declared scope, enforced by **wave-level pre-authorisation** - the broker's meter is post-hoc (`spendMeter.charge` after completion, `lwd-model-broker.js:818`; gate at `:858`; $1/day default at `:104`), so the host prices each rewrite wave against remaining headroom (readable via `/healthz`, `:1282`) before dispatch and pauses before burning rather than after. Overshoot is bounded to one wave and disclosed. A budget death mid-run lands as the existing honest pause, never a failure: landed documents stay reviewable, the ledger names the split, and "Retry remaining" is the surgical re-entry (`retryFailedDocs` pattern, `livingDocsService.ts:5830-5850`).

**What survives of the fan-out, verified:** token-budgeted packing (`planFanoutBatches`, `common/fanoutBudget.ts:71`) as the context packer; per-document attribution with partial success (`:6130-6139`); surgical retry; honest terminal states (`summarizeFanoutRun`, `common/fanoutOutcome.ts:79` - "the all-clear is reachable only when there were no failures and no pause"); the policy dial's double enforcement (`:6060-6063`, `:6203-6204`). What dies, by design: the one-shot multi-document JSON prompt (`:6038-6045`) and title-string routing (`:6146-6150`) - tools address documents by docId, which structurally kills F9.

**Steering:** the steps feed (`onStep`/`addStep`, `:6116`, `:6141`) becomes the loop ledger; the fan-out progress record (`:560-562`, `:6086-6087`) generalises to "step K - reading X / rewriting Y"; stop is the existing canceller (`:5961`); pause is the existing budget pause (D15 semantics, `:5135`, `:5938-5944`). The scope card is the one new consent surface.

### 2.5 D5 - no framework, and why

The repo already contains an upstream agent framework the brief missed entirely: `src/vs/platform/agentHost/`, a separate Node process running Claude Agent SDK sessions with permission-gated tools (`claudeAgent.ts:495`, `:766`, `:1042-1052`; `@anthropic-ai/claude-agent-sdk` at `package.json:168`; upstream provenance confirmed via git log). It was examined as a candidate and rejected: it drives the Claude Code runtime with a filesystem/bash tool surface and Anthropic auth, bypassing the broker that owns metering, the spend cap and the audit trail - the product's one economic control point - and it anchors the loop in a desktop-only process. The SDK `toolRunner` was rejected because the broker implements a subset of the Messages surface and adopting the client pressures it to fake the rest (plus a live proxy-breaking header bug, anthropic-sdk-typescript#922). Vercel AI SDK was rejected because its core value, the provider abstraction, is something this product already owns - the broker is the provider abstraction - and layering it adds a second translation layer plus a large renderer dependency. LangGraph is the wrong weight class.

What is built instead: `common/livingDocsAgentLoop.ts`, a pure Anthropic-Messages tool-use state machine (~300-500 lines), no VS Code imports, injected model client and tool registry, typed events, wire shapes typed against `@anthropic-ai/sdk` (types only, `package.json:97`). It joins the codebase's existing family of pure tested seams (`spendMeter`, `planFanoutBatches`, `summarizeFanoutRun`) and the broker's `node --test` suites pin the per-door tool passthrough contract.

### 2.6 D7 - cost and latency

Prompt caching is absent (`cache_control`: zero hits in `src/` and `scripts/`) but flipping it on today would buy nothing: the system prompt is ~300 tokens (below every provider's 1024-token cache minimum) and every turn re-serialises a mutating document ahead of a sliding six-turn transcript window (`:5981`, `.slice(-6)` at `:6191-6199`), so no prefix survives. The restructure is the work: stable system prompt and tool definitions, document snapshots pinned early as append-only tool results (a mutation is a new read event, never an edit to history), digest-only rewrite receipts, breakpoint on the latest turn. OpenRouter passes caching through per provider (Anthropic 1.25x write / 0.1x read via explicit breakpoints; OpenAI automatic >= 1024 tokens) and does sticky provider routing for ~10 minutes after a cache hit, steered by a per-conversation `session_id` - without it a mid-loop provider failover goes silently cold. The Codex OAuth door already caches server-side (`prompt_cache_key`, `prompt_cache_retention: "24h"` in the recorded fixture, `scripts/test/fixtures/codex-responses-stream.sse:2,38`); the broker should send a stable per-conversation key as Codex CLI does.

Realistic 20-document task (15 targeted + 5 rewrites, 15-step loop): ~$1.25 uncached falls to ~$0.60 cached (50-60% task-level; per-step time-to-first-token drops from prefilling ~20k tokens to ~1.5k), plus ~$0.06 of rewrite output. Wall clock ~40-50s with progressive landing; worst case (20 x 10KB true rewrites) ~2-2.5 minutes of background emission while review proceeds. That sits at 60-75% of the $1/day default cap, which stays by founder ruling (9.1); the relief valve is steering users to the OAuth door so they spend their own credits, and the wave pre-authorisation in 2.4 is what makes the collision honest rather than surprising.

Serving hygiene that the wall-clock silently depends on: the broker forwards a reasoning knob per door (today `thinking`/`output_config` die in translation, `:379`, `:482-491`) with rewrite lanes at minimal effort; per-purpose `max_tokens` (the global 1024 at `livingDocsService.ts:203` is a truncation machine; the Codex door cannot express a cap at all, `:469-474`, so truncation detection there is length-sanity); the single global `_modelLimiter` (`:5130`, concurrency 2 at `:241`) becomes per-purpose so an 8-wide rewrite wave does not unthrottle everything else; retries gain jitter and 429 backoff so a transient failure during a wave cannot thundering-herd at 2x wave width (`:5126-5141`, `:5239-5250`).

For web deployments one decision is recorded now: the served web client's CSP is `connect-src 'self' ws: wss: https:` (`src/vs/server/node/webClientServer.ts:445`), so plain `http://localhost:8090` is blocked; the broker must be reached over https or mounted as a same-origin reverse-proxy path. Desktop is unaffected. (Deferred: web serving is out of v1.0 by founder ruling 9.6; browser checks are a local HTML pseudo test for now.)

### 2.7 D8 - the invariant set

Stated fully in section 5. The D8 headline: deterministic checks carry every guarantee; a second model pass never does. One cheap-tier structured pass ("every planned edit maps to a hunk; flag hunks no plan line explains") runs only on whole-document rewrites above a hunk threshold and on binding-adjacent edits, budget-capped, and its absence degrades to an honest `unverified` label - never a block, never an `approved` record.

## 3. The system, end to end: a twenty-document turn

1. The user types "update the whole project for the new pricing" with no attachments. Tier 0 does not fire; the planner gets the catalogue and declares `plan_scope` with 14 documents and a rationale.
2. The scope card holds the run: "I found 14 documents that mention the old pricing", chips expanded and removable, Proceed / Narrow. One click.
3. The loop reads the targeted documents (ordinal-labelled), emits segment lists per document, and receives per-segment receipts. Targeted changes land instantly in the change store and appear in the review surfaces per document.
4. The loop dispatches one `rewrite_documents` call for the five documents needing full rewrites. The host prices the wave against the per-task budget and daily headroom, then runs the calls 6-8 wide at minimal reasoning effort. Bodies stream into the store; the host diffs each into Changes; documents flip from "writing..." to reviewable as each completes. The loop receives digests.
5. The user starts reviewing document 1 while documents 12-14 are still writing. A mid-run approval bumps that document's revision; the store's write boundary rejects any in-flight change against the stale base for overlapping spans (`stale-base`), and the host injects a re-read notice into the transcript. Human decisions dominate in-flight agent output, structurally.
6. The loop calls `finish`; the host composes the ledger from receipts ("14 documents changed - 63 changes; 2 documents skipped by policy, said so") and the run-end overlap check adds "3 other documents also mention pricing - widen and re-run?".
7. Review proceeds per section 4; every approval journals an intent, splices, records a post-hash; the receipt lands when the last change is decided.

## 4. The UX specification

### 4.1 Scope chrome

Agent-added scope renders as ghost chips in the existing attach-chip row above the composer (`reviewRailView.ts:1923`, capped with the expander per #177 at `:103`): dashed border, secondary ink, an "agent" marker, hover shows the rationale, removable like any chip; at high counts the row collapses to "14 documents - 3 added by agent". Provenance (whose hand added which document) persists into the audit trail. The hold gate renders as an agent turn in the transcript with the chip list inside and two verbs: **Proceed** (filled indigo - legitimately, because consent-to-scope is a run-consent verb, not a content bulk verb; the never-filled rule binds bulk content verbs) and a quiet "Narrow...". The run-outcome widen line carries a quiet link-verb, "widen and re-run?", with each named document openable first; a widened re-run lands additional Changes in the same set.

### 4.2 The run, live

The reveal unit is the completed document: a rewrite mid-stream shows as an indigo "writing..." row, not reviewable. Start review appears with the first complete document. During a live run the ledger prints three honest registers - "12 decided - 18 waiting - 5 documents still writing" - and never a denominator pretending to be final; "M of N" and the green receipt appear only when the run terminates. A document that had gone all-clear and receives new changes re-enters the changed list; if the user is viewing it, the bar gains a quiet "2 new changes" affordance and never reshuffles under the cursor (pull, not push).

### 4.3 The review hierarchy, completed

Individual edit: ships (plan 52 WP-A), re-addressed by `{baseRevision, span}` ordinals instead of anchor text - which closes the #300 class (the one decoration that survived #300 was the ordinal-zipped gutter, the codebase's own proof that positional addressing works where text-anchor addressing breaks). Document level: per-document bulk verbs ship (`reviewRailView.ts:702-717`); a previous-document control is added (`nextPendingDocId` cycles forward only, `livingDocsModel.ts:383`; no prev symbol exists in the contrib - review is not monotonic). Change-set level: ships, re-founded on the store so the three levels are folds of one object and cannot disagree.

**Requirement 4, kept literally:** every scale views as a line-by-line diff. For a rewrite-class document the default first view is the whole document as one continuous diff in reading order - unchanged prose plain, changed spans word-grain up to the recorded ~60% threshold, WAS/NOW past it, insertions all-additions as the shipped insert path renders them (`livingDocsModel.ts:365-368`). "View clean" is a secondary toggle, never the default. What changes for rewrite-class is the *decision unit*: the one-canonical-card promote ceremony (`livingDocRender.ts:1562-1566`) is suspended, every hunk carries lightweight in-place verbs, and the document header card carries the primary verbs ("This document was rewritten - 38 of 42 blocks changed", Approve document... / Reject document... / comment). Diff-first viewing at every scale; document-first deciding for rewrite-class only; per-hunk deciding always available.

### 4.4 Directional bars

Asymmetric, an evolution of `docReviewBar` (`livingDocRender.ts:1598-1646`), not two clones. The top bar keeps the count sentence, kind breakdown, Review each, quiet Approve all..., Next document and Approve everywhere..., and gains a directional segment ("3 above ^") only when undecided changes lie above the viewport. The bottom bar is new, thin and navigation-only ("5 below v"); it never carries verbs. Both-directions state: both segments show; nothing merges. The recorded rules survive: bulk verbs never filled and host-confirmed; no bulk verb at exactly one pending change (`:1620-1628`); disappearance is the done signal - with the one conscious revision that "done" means zero *undecided* (pending + discussing + needs-attention), or the bar would vanish over open threads. Counts trade in one currency, decisions, everywhere (bars, rail, chat note, confirm sentences); groups are presentation. Colour mints nothing: amber chrome ("waiting on you", the hue law at `common/abstractTokens.ts:17-20`), kind badges reuse the shipped meaning/figure colours, `needs-attention` maps to the existing `askFirst` token, discussion is carried by the comment glyph, never colour alone.

### 4.5 Comment as a third verb

The thread is an orthogonal fact (`hasOpenThread`), not a status peer - a change can need attention *and* be under discussion. Bulk eligibility is one predicate living only inside `captureBulkSet`: `status === 'pending' && !hasOpenThread`. Approve and Reject stay live on a discussing change; discussion is an annotation and a re-entry point, never a lock. The inline card gains a quiet Comment verb beside Approve/Reject/Tweak (Tweak is the shipped prior art for human amendment, `livingDocsModel.ts:371-375`); commenting collapses the card to "Discussing - 2 replies". An agent revision appears as the new NOW with a version stepper ("v2 of 2 - see v1"), earlier versions collapsed, never deleted; the approve verb names its object ("Approve v2"). Re-entry is scoped to the change's document, span context, instruction and thread - a fraction of a full turn. Bulk confirm sentences name exclusions, never drop them: "Approve 9 changes? 2 under discussion and 1 needing attention are not included." The thread and version chain land in the audit trail; the exchange is provenance for why the change landed as it did.

### 4.6 File-level operations

`ChangeKind` gains `structure` (create/delete/rename/move), badged mono, coloured by existing semantics (create in the green diff family, delete red, rename neutral ink with a mono from->to). Create: the document is the decision - an all-additions diff with header verbs, no hunk-level verbs (rejecting half a new document is editing, not reviewing; Tweak and the thread are the escape hatches); directional bars suppressed inside it. Delete: the highest-stakes op, presented to be read first - the card names the cost ("Deletes 'Old pricing FAQ' - 42 blocks - last edited 3 May"), the document opens under a full-width red-edge "Proposed for deletion" banner carrying the verbs; the comment verb is the designed renegotiation path. Rename: a one-line card naming the inbound wikilink rewrites, which travel in the same Change. **Bulk participation: creates and renames are bulk-eligible; a delete never is, at any level** (confirmed by founder ruling 9.5) - asymmetric reversibility justifies the asymmetry, and the sentence names it: "Approve 12 changes? 1 proposed deletion is not included - decide it in the document." Cross-document moves are one Change with two anchors and one decision; bulk membership requires all anchors in scope, otherwise excluded and named. Sentence grammar: plain edits appear as counts; moves and deletes appear by name.

### 4.7 Done, and the residue

Three concentric done signals: a decided change's widget resolves into settled prose; a clear document's bar goes green then disappears; the set's amber note flips to a green receipt - "All 63 decided - 58 approved - 5 rejected - restore point saved", with `needs-attention` residue named ("61 decided - 2 need attention"). After any bulk verb the surfaces narrow to exactly the discussing and needs-attention items: review converges on the things that genuinely need a human. The skip report from shrink-only bulk application surfaces as the residue funnel ("2 were not approved - 1 under discussion, 1 changed underneath"), never as a silent difference. The design's success metric: per-document triage must stay cheaper than surrender (Approve all).

## 5. Invariants: what makes silent failure impossible

The change store is a project-level, append-only journal + snapshot (`.abstract/changes/`), the single authority for counts, verbs, receipts and audit. The per-doc `.lock.json` audit and the activity-feed ledger (`common/livingDocLedger.ts:9-19`) become derived views, rebuilt idempotently, never written directly. The API is the invariant carrier: `propose(batch) -> receipts`, `captureBulkSet(scope)`, `approveByIds / rejectByIds`, `comment`, `amend` - no `setStatus`, and the query-based `approveAll(docId)` / `approveAllPending()` are deleted from the public surface so a call site *cannot* re-derive a set.

| # | Invariant | Impossibility mechanism |
|---|---|---|
| **I1** | Apply outcomes are a closed result type; silence is unrepresentable. | `applyBlockEdit`'s `string` return dies (its anchor-miss path `return blockText`, `livingDocMarkdown.ts:759`, is indistinguishable from success by construction). Every apply primitive returns `{landed, postHash} \| {landed: false, reason}`; the store's only terminal writer refuses `approved` without a postHash. |
| **I2** | An approval is written only by the code path that mutated the document, carrying the post-state hash; every surface is a fold. | Kills #329's *two* record-despite-failure paths (`livingDocsService.ts:6358` fall-through and `:6363` no-op, then `:6375-6381` unconditional) and the dual independent records (transcript `:5404-5419` vs lock, where `_persist` can abandon `:6739-6742` or swallow `:6759-6761`). Single writer; a failed persist is a state transition to `needs-attention/unverified`, never a standing `approved`; a startup reconciler re-verifies journalled post-hashes against disk. |
| **I3** | Every model claim reconciles against the store's receipts before the reply renders. | Kills both #303 mechanisms - parse degradation (F2) *and* the confirmed one, queue-time silent drops (`:6211` headings, `:6205` policy, `:6212-6222` similarity, `:6226` binds, `:6147` title miss - all bare `undefined` today). The reply renderer's signature takes `(finishSummary, receipt)`; prose cannot reach the bubble without the receipt; claimed > 0 with queued = 0 renders as a failure. |
| **I4** | A bulk verb operates on an immutable id snapshot captured with its confirm sentence; the applied set may shrink, never grow. | Kills #334 at all three call sites (`livingDocEditor.ts:320` -> `:6398`; `reviewRailView.ts:708` -> `:714`; `:752` -> `:6444`) and the unconfirmed chat-level bulk (`:1164`, `:1167`). `captureBulkSet` is the only path; eligibility lives inside it; `approveByIds` re-checks per id and reports skips. |
| **I5** | Change identity, state and count have exactly one persisted home. | `_pending` (memory-only, `:462`) is replaced by the store; documents are addressed by URI, never title; terminal states are immutable; revisions stack as versions on one id. |
| **I6** | Untouched content is proven untouched. | Targeted approves splice raw text (unchanged bytes unchanged by construction, plus arithmetic post-conditions); model-emitted bodies verify declared keep-range checksums against base spans; after every approve, `diff(pre, post)` must equal exactly the approved hunk - total over unknown failure modes, and it also catches serialiser lossiness. |
| **I7** | Ingest failures are terminal states, never degradations. | Schema-invalid payloads are failed turns with bounded re-ask; `stop_reason: max_tokens` on any body-emitting call is a hard fail. |
| **I8** | No change computed against a superseded revision may apply to an overlapping span. | The store's write boundary judges validity against journal order atomically with admission. Non-overlapping staleness is deterministically rebased (`queued(rebased)`); overlap lands as recorded-and-ineligible `needs-attention (stale-base)` - never discarded (a silent drop wearing a safety argument), never applied over a human decision. The dispatcher's re-read-before-propose is a cost optimisation; the executor is the guarantee. |

**Journal discipline:** J1 intent (change ids, verb, actor, per-doc baseHash + **expectedPostHash** + snapshot id) appended and fsynced before any mutation; M mutations one document at a time in insert-before-delete order (every crash window fails towards visible duplication, never silent loss); J2 per-doc commit with postHash; J3 resolution-final; derived views rebuilt after. Records carry length + checksum; recovery truncates torn appends. Because the expected post-hash is declared before the write, the reconciler can *prove* the mutated-but-unjournalled window: disk hash equals the declared expectation -> `applied (recovered)`; equals base -> retry offered as `partially-applied`/`interrupted` (never auto-retried at startup); equals neither -> `unverified`, no auto-action. Multi-anchor resolutions carry per-anchor outcomes; `partially-applied` is a first-class, named, non-terminal status ("The moved text was added to B but could not be removed from A - it currently appears in both places", with retry-delete-side and undo-insert-side as the recoveries). Disk-full fails closed at J1 ("Couldn't record this approval, so nothing was changed" - UI, not a log line); a journal failure after mutation freezes new intents until an append succeeds.

## 9. Founder rulings (20 Aug 2026)

The six questions were put to the founder and answered the same day; they are recorded here as constraints on the build, phrased question then ruling.

1. **The daily budget - the $1/day cap stays.** The app has to be valuable at a $30/month price point or the margins are simply not there, and the included tier is founder-funded. The relief valve is the OAuth door: the product must actively encourage signing in with OpenAI OAuth so users spend their own credits, and the model picker must make the provider choice - included OpenRouter tier versus the user's own OpenAI account - explicit and selectable. This folds directly into the D2 pinning work (2.2): door choice becomes a first-class, visible part of model selection rather than an implicit fallback.
2. **The worst-case rewrite wait - accepted for this stage.** Roughly 2-2.5 minutes of background writing, with review starting on the first finished document, is acceptable. The fast-apply fallback lane stays behind its interface and is not promoted now.
3. **The included planner - Sonnet 5 for both roles.** `anthropic/claude-sonnet-5` is approved as both the planner and the rewrite author on the included tier. Opus-as-planner with Sonnet-as-applier is the stated aspiration if margins ever allow; not now.
4. **Reads outside scope - allowed.** Reading other project documents for context is a good idea; every read is disclosed in the run ledger. The agent architect's position is adopted as ruled, and the dissent in section 10 is closed.
5. **Deletes and bulk - confirmed.** A proposed deletion is never included in any bulk approve, at any level; it is decided in the document.
6. **Web serving - out of v1.0.** Hosted web deployment was never intended for v1.0. Where a browser check is needed, it is a local HTML opened in the browser as a pseudo test, not a hosted page. The CSP/same-origin note in 2.6 stands as a pre-recorded decision for whenever web serving does land; it constrains nothing now.

## 10. Recorded movements and dissent

The council converged through argued concessions rather than compromise; the movements are part of the record:

- The **inference engineer withdrew** Morph-as-spine after the emit-matrix exchange, on the grounds that their own affordability numbers argued the other side; retained as conditions the anchor echo, the merged detection layer, and the measured escape hatch (schema-violation rate >= ~5% per model flips that model to the lazy-edit + Morph lane).
- The **document-systems engineer conceded** the single-stream latency point (a planner must never emit twenty bodies serially) while holding that the changed prose must be planner-authored; the parallel-call design is the synthesis.
- The **agent architect withdrew** model-authored per-document `finish` statuses (the host composes the ledger from receipts; the model narrates) and the mid-run consent dialog for explicit scope (fails-closed with the model relaying in words is stronger).
- The **review designer conceded** that "clean read first" for rewrites would have quietly weakened requirement 4; the diff-first/decide-at-document-level split is the refinement.
- The **retrieval engineer conceded** the deterministic open-document default (a keyword matcher's false negatives are exactly the silent under-scope the design exists to prevent); every unattached ask now routes through the planner.

**Standing dissent, one item.** The agent architect holds that out-of-scope *reads* should remain permitted-but-ledgered (adopted, and since confirmed by founder ruling 9.4 - the dissent is closed and kept for provenance). Should reads ever be flipped to fail-closed, the recorded objection stands: blocking reads degrades edit quality for zero trust gain, since reads are non-destructive and the ledger keeps them visible. A middle position (wikilink-adjacent reads only) is noted as acceptable to all parties.

**One trade the council did not decide** was the worst-case rewrite wait versus prose quality; the founder has since ruled it (9.2): the wait is accepted for this stage. The architecture keeps both lanes open behind one interface so revisiting is a configuration, not a rebuild.
